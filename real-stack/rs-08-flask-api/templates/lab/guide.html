📖 Real Website Guide — testing a JWT REST API

Fingerprint drill — prove what you are looking at

  • JSON everywhere: responses carry Content-Type: application/json even for errors — you are testing an API, not a website. The one HTML surface (the profile page) is the companion.
  • The token: log in and look at the credential: three base64url segments separated by dots is a JWT. Decode the first two — header (alg: HS256) and claims — no tool but base64 needed. The third segment is the signature, and everything rides on its secret.
  • Server header: Werkzeug/3.x Python/3.12 — a Flask dev server in production clothing.
  • Error shape: deliberately break a request and read the reply. Real APIs leak stack traces, paths and config in errors more often than their teams believe.
  • Object ids: sequential numbers in URLs (/users/3/workouts) are an invitation to test authorization on every object, not just authentication.

The API testing workflow

  1. Map the surface: the landing page's endpoint map is what the client admits to. Note every verb, every id, every writable field.
  2. Get a real token: register or log in through Burp so every request is captured. Send the login to Repeater — that token is your baseline identity.
  3. Interrogate the token: decode the claims. Ask: what does the server trust from this document? Flip is_premium, re-sign nothing, send it — does claim editing alone work? Then ask the harder question: what signed this, and is it guessable? An offline dictionary attack against the signature (hashcat mode 16500, or jwt_tool) answers that without touching the server again.
  4. Walk the objects: with your low-privilege token, request other users' objects by id — workouts, profiles, exports. Authorization bugs (BOLA) are the most common critical finding in real API assessments.
  5. Send fields nobody offered you: registration and update endpoints that bind the whole request body will accept privileged columns. Diff the documented fields against the columns the responses reveal.
  6. Read the responses, not the requests: over-exposure hides in successful replies — full rows where three fields were needed, hashes where none were.
  7. Mind the server-side fetchers and the money paths: any "import from URL" feature is SSRF-shaped; any check-then-act balance flow is race-shaped. For the race, Burp's parallel send (or Turbo Intruder) fires both requests inside the same pause.
  8. Count the failures: ten bad logins with no throttle is a finding even before any password falls.

The professional habit

Note every flaw as: what, where, proof, impact. The Complete page will ask you to write one up properly — that write-up is what a client actually pays for.
