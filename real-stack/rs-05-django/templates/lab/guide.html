📖 Real Website Guide — recognising Django

Fingerprint drill — prove it is Django before you test

  • Cookies: sessionid and csrftoken are Django's defaults, set before you even log in.
  • The admin: /admin/ answers with Django's unmistakable login page ("Django administration").
  • Error pages: with DEBUG on, the yellow technical page names the URLconf, the exception and the settings module — the framework introducing itself.
  • Form fields: a hidden csrfmiddlewaretoken input in every honest form; its absence somewhere is a finding, not a detail.
  • Password format: Django stores algorithm$salt$hash — the algorithm prefix tells you the hasher that was configured when the password was set.
  • WhatWeb: whatweb http://localhost:3205 names Django, its session cookie and the admin route in seconds.

What to test first on a real Django site

  1. Settings, not code: DEBUG, ALLOWED_HOSTS, the first entry of PASSWORD_HASHERS, a SECRET_KEY you can find in a leaked repo. Django's defaults are strong; deployments are not.
  2. Every place the ORM was bypassed: raw(), extra(), RawSQL — search pages and "legacy reports" are the usual suspects.
  3. Templates with |safe, mark_safe or autoescape off — the framework's main XSS defence, disabled by hand.
  4. ModelForms: fields lists that include privilege attributes (is_staff, role, balance) reused on public pages.
  5. @csrf_exempt — grep for it in any source you receive; every hit on a state-changing view is a report line.
  6. /admin/ hygiene: default or install-day credentials, no MFA, reachable from the internet.
  7. Login behaviour: does the session key change at login? Django's auth.login() cycles it — a hand-rolled login often does not.

Burp workflow for this lab

Proxy the portal and map it with the site map. Keep two browsers (or two cookie jars) — patient and doctor — to feel the IDOR and the |safe message properly. Work the record search in Repeater: compare a normal query against a tautology and watch whose records come back. Send the appointment-cancel POST from Repeater with the token stripped and no Referer. Note your sessionid cookie before and after login in Comparer. The debug page you trigger on a malformed record URL is worth a screenshot for your report — it is the finding, verbatim.

The professional habit

Django findings read best as "the framework already prevents this; the deployment switched it off" — with the setting or the line as evidence. The Complete page will ask you to write one up properly, and to prove the MD5 finding by actually cracking a hash.
