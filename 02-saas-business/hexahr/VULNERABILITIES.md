# HexaHR — Vulnerability Map (24 scored tests)

Every vulnerability below is a **scored test** in the lab's progress system. A test completes only when the server detects the exploit actually succeeding — there is no "mark done". Grouped by feature; counts match the in-app **🎯 Tests** page exactly.


## Login & Authentication — 6 test(s)

### SQL Injection Login Bypass
- **OWASP:** A03 Injection · **Difficulty:** Beginner · **Severity (in a real client report):** Critical
- **What it is:** String-built queries let attacker input change the query logic itself. Parameterised queries make input data-only, so a login bypass like this becomes impossible.
- **Business impact:** On a real HR system this is a full account takeover of the most privileged account — every salary, bank detail and personal record in the company is exposed in one request.
- **Report title:** SQL Injection in Login Form Allows Authentication Bypass
- **Fix:** Use parameterised queries / prepared statements everywhere; never build SQL by string concatenation.

### Brute Force — No Rate Limiting
- **OWASP:** A07 Authentication Failures · **Difficulty:** Beginner · **Severity (in a real client report):** High
- **What it is:** Without rate limiting, lockout or MFA, an attacker can try unlimited passwords against any account. The 10th failure being processed like the 1st is the flaw.
- **Business impact:** Attackers routinely crack employee accounts this way, starting with the weakest passwords. One guessed HR password exposes the whole company's payroll.
- **Report title:** Missing Rate Limiting / Account Lockout on Login
- **Fix:** Throttle attempts per account and IP, add progressive delays or lockout, and enforce MFA for privileged roles.

### User Enumeration via Login & Forgot-Password
- **OWASP:** A07 Authentication Failures · **Difficulty:** Beginner · **Severity (in a real client report):** Medium
- **What it is:** Different responses for "account does not exist" and "wrong password" hand attackers a verified list of employee accounts to target with phishing and password attacks.
- **Business impact:** An attacker can harvest a real staff directory of emails from a client's HR portal, then aim password spraying and spear-phishing at confirmed accounts only.
- **Report title:** Account Enumeration via Differential Authentication Responses
- **Fix:** Return one generic message ("if this account exists, we sent instructions") for all login and reset outcomes.

### Weak / Default Credentials
- **OWASP:** A07 Authentication Failures · **Difficulty:** Beginner · **Severity (in a real client report):** High
- **What it is:** Default and never-rotated credentials are one of the most common real-world breach causes. First-login forced password change and a default-credential audit close this hole.
- **Business impact:** An attacker who guesses one default password gets a genuine employee account — a foothold inside the client's HR system with access to colleagues' personal data.
- **Report title:** Default Credentials Still Active on an Employee Account
- **Fix:** Force a password change at first login, disable vendor defaults, and audit for unchanged issued passwords.

### Predictable Password-Reset Token
- **OWASP:** A07 Authentication Failures · **Difficulty:** Intermediate · **Severity (in a real client report):** Critical
- **What it is:** Reset tokens must be long, random and single-use. A token computed from the email address can be generated by anyone who knows the algorithm — the mailbox check is pure theatre.
- **Business impact:** Anyone on the internet can reset the HR admin's password knowing only her email address, taking over the entire HR platform without touching her inbox.
- **Report title:** Password-Reset Tokens Are Predictable (Derived from Email)
- **Fix:** Generate reset tokens with a CSPRNG (≥128 bits), store only a hash, expire quickly, and invalidate after use.

### Session Cookie Role Tampering
- **OWASP:** A01 Broken Access Control · **Difficulty:** Intermediate · **Severity (in a real client report):** Critical
- **What it is:** Authorization data must live server-side or be cryptographically signed. If the client can edit its own role, every role check in the app is decoration.
- **Business impact:** Any ordinary employee can promote themselves to HR admin by editing a cookie — no password, no exploit tooling, just a browser extension.
- **Report title:** Client-Controlled Role in Session Cookie Enables Privilege Escalation
- **Fix:** Keep roles in server-side session storage, or sign session tokens (e.g. HMAC/JWT with a server secret) and verify integrity on every request.


## Employee Directory & Search — 3 test(s)

### SQL Injection in Employee Search
- **OWASP:** A03 Injection · **Difficulty:** Intermediate · **Severity (in a real client report):** High
- **What it is:** Injection in search is a data-exfiltration channel: crafted input can dump records the UI deliberately hides, far beyond what the search box was meant to show.
- **Business impact:** A hidden executive-compensation record — the most sensitive row in the database — leaks to any employee through the ordinary search box.
- **Report title:** SQL Injection in Employee Search Exposes Restricted Records
- **Fix:** Parameterise search queries and enforce record-visibility rules in the query itself, not in the UI layer.

### Reflected XSS in Employee Search
- **OWASP:** A03 Injection · **Difficulty:** Beginner · **Severity (in a real client report):** High
- **What it is:** Any user input reflected into a page must be output-encoded. A search box that echoes raw input turns a link into a script-delivery weapon against colleagues.
- **Business impact:** An attacker emails an employee a crafted search link; opening it runs script in the victim's logged-in HR session — session theft or actions performed as the victim.
- **Report title:** Reflected Cross-Site Scripting in Employee Search
- **Fix:** Context-encode all reflected user input on output and add a Content-Security-Policy as defence in depth.

### IDOR — Full Employee Record Exposure
- **OWASP:** A01 Broken Access Control · **Difficulty:** Beginner · **Severity (in a real client report):** High
- **What it is:** Every object access must check that the requester may see that object. Sequential ids plus no ownership check means the whole staff directory's private data is public to insiders.
- **Business impact:** Any employee can read every colleague's home address, personal phone and date of birth — prime material for identity theft, stalking and targeted phishing.
- **Report title:** Insecure Direct Object Reference Exposes Employees' Personal Data
- **Fix:** Enforce per-object authorization (owner, same-department manager, or HR) on every record view; minimise the fields shown.


## Payroll — 2 test(s)

### Payroll IDOR — Colleague's Salary & Bank Details
- **OWASP:** A01 Broken Access Control · **Difficulty:** Beginner · **Severity (in a real client report):** Critical
- **What it is:** Payroll is the most sensitive data an HR system holds. Object-level authorization is not optional: the server must verify the payslip belongs to the requester (or a privileged role) on every request.
- **Business impact:** Every employee can see every colleague's exact salary and full bank details — a confidentiality breach that destroys trust and invites fraud and discrimination claims.
- **Report title:** Insecure Direct Object Reference in Payroll Exposes Salary and Bank Data
- **Fix:** Check ownership or privileged role server-side for every payroll record; log access to payroll data.

### Cross-Department Payroll Access
- **OWASP:** A01 Broken Access Control · **Difficulty:** Intermediate · **Severity (in a real client report):** High
- **What it is:** Role checks alone are not enough; scope matters. A manager role must be bound to their own department — "is a manager" is not "may see all payroll".
- **Business impact:** A single curious or malicious manager can harvest the entire company's salary table department by department, enabling poaching, blackmail and pay-equity disputes.
- **Report title:** Missing Department Scoping Allows Cross-Department Payroll Access
- **Fix:** Scope manager queries to their own department server-side; only HR admin gets a company-wide view.


## Leave Management — 3 test(s)

### Leave Self-Approval
- **OWASP:** A01 Broken Access Control · **Difficulty:** Beginner · **Severity (in a real client report):** High
- **What it is:** Approval workflows must enforce separation of duties server-side: requester ≠ approver. A missing check turns every approval process into self-service.
- **Business impact:** Employees grant themselves unlimited leave without any manager ever seeing it — payroll pays for holidays nobody approved, and absence records become fiction.
- **Report title:** Leave Requests Can Be Approved by the Requester (Missing Separation of Duties)
- **Fix:** Require approver ≠ requester and approver to be the requester's manager or HR, enforced server-side.

### Leave Approval Across Departments
- **OWASP:** A01 Broken Access Control · **Difficulty:** Intermediate · **Severity (in a real client report):** Medium
- **What it is:** Workflow authorization must match the org chart: approvers act within their reporting line. Without it, approvals are meaningless and audit trails lie.
- **Business impact:** Managers can approve or sabotage leave outside their team — covering up absences, playing favourites, or creating fraudulent attendance records across the company.
- **Report title:** Leave Approvals Are Not Scoped to the Approver's Department or Reporting Line
- **Fix:** Restrict approvals to the requester's direct manager (or HR), verified against the org structure server-side.

### IDOR — Reading Colleagues' Leave Requests
- **OWASP:** A01 Broken Access Control · **Difficulty:** Beginner · **Severity (in a real client report):** Medium
- **What it is:** Leave reasons are health-adjacent personal data. Object-level checks apply to workflow objects just as much as to records and payslips.
- **Business impact:** Staff can read why colleagues are absent — including medical and family reasons — a serious privacy breach and, in many jurisdictions, a data-protection violation.
- **Report title:** Insecure Direct Object Reference Exposes Leave Request Details
- **Fix:** Limit leave detail visibility to the requester, their manager and HR.


## Profile & Account — 4 test(s)

### Mass Assignment — Self-Promotion & Salary Edit
- **OWASP:** A01 Broken Access Control · **Difficulty:** Intermediate · **Severity (in a real client report):** Critical
- **What it is:** Bind only allowlisted fields on update. Anything the client sends — role, salary, balance — must never be copied blindly onto the record.
- **Business impact:** An employee quietly raises their own salary in the HR system of record; payroll then pays the fraudulent amount as if HR had approved it.
- **Report title:** Mass Assignment in Profile Update Allows Salary and Role Tampering
- **Fix:** Use an explicit allowlist of updatable fields per role; reject or ignore privileged fields (role, salary, department) from self-service updates.

### Stored XSS via Display Name
- **OWASP:** A03 Injection · **Difficulty:** Intermediate · **Severity (in a real client report):** High
- **What it is:** Stored XSS is worse than reflected: one malicious profile poisons every page that renders the name, including admin screens — a direct path to session theft of privileged users.
- **Business impact:** An employee plants a script in their name; when the HR director opens the directory, the script runs in her session and can act as her — full HR takeover from a profile field.
- **Report title:** Stored Cross-Site Scripting via Employee Display Name
- **Fix:** Output-encode user-controlled fields at render time everywhere; validate names against a safe character policy.

### CSRF on Profile Update
- **OWASP:** A01 Broken Access Control · **Difficulty:** Intermediate · **Severity (in a real client report):** Medium
- **What it is:** State-changing requests need an unguessable, session-bound token (or strict SameSite cookies). Cookies alone authenticate the browser, not the user's intent.
- **Business impact:** A malicious website an employee visits while logged in can silently rewrite their profile — name, phone, even bank-adjacent fields — without them clicking anything in the HR app.
- **Report title:** Cross-Site Request Forgery on Profile Update
- **Fix:** Require a per-session CSRF token on all state-changing forms and verify Origin/Referer as defence in depth.

### Weak Password Policy
- **OWASP:** A07 Authentication Failures · **Difficulty:** Beginner · **Severity (in a real client report):** Medium
- **What it is:** Password policy is a control, not a suggestion: enforce a sane minimum length and screen against known-breached passwords, especially where payroll data is at stake.
- **Business impact:** Employees who choose one-character passwords hand attackers an easy win — combined with no rate limiting, those accounts fall in seconds.
- **Report title:** No Password Complexity or Length Policy Enforced
- **Fix:** Enforce ≥10–12 character passwords, check against breached-password lists, and apply the policy on every set/change path.


## Admin Panel — 1 test(s)

### CSRF on Admin Action (Deactivate Employee)
- **OWASP:** A01 Broken Access Control · **Difficulty:** Advanced · **Severity (in a real client report):** High
- **What it is:** Privileged actions need CSRF protection most of all: one malicious page open in the HR admin's browser can fire destructive admin requests with her authority.
- **Business impact:** An attacker who lures the HR director to a booby-trapped page can deactivate employees at will — sabotage and denial of service against the client's workforce records.
- **Report title:** Cross-Site Request Forgery on Administrative Employee Deactivation
- **Fix:** Enforce CSRF tokens on all admin actions, require re-authentication for destructive operations, and audit admin activity.


## API & Data Exposure — 3 test(s)

### Weak Static API Token
- **OWASP:** A07 Authentication Failures · **Difficulty:** Beginner · **Severity (in a real client report):** High
- **What it is:** API keys must be long, random, per-client and rotatable — and never printed in documentation or comments. A static guessable key is public access with extra steps.
- **Business impact:** Anyone who reads the public API docs walks away with a working key to the employee API — names, emails, departments and salaries included.
- **Report title:** Guessable Static API Key Disclosed in Documentation
- **Fix:** Issue per-client random API keys (≥128 bits), store them hashed, support rotation, and scrub secrets from docs and comments.

### Unauthenticated Employee Data Export
- **OWASP:** A01 Broken Access Control · **Difficulty:** Beginner · **Severity (in a real client report):** Critical
- **What it is:** Every endpoint needs authentication and authorization — especially exports, which concentrate the most sensitive data into a single response.
- **Business impact:** The whole company's HR database — every salary and bank account — is downloadable by anyone on the internet with zero credentials. This is the headline breach.
- **Report title:** Unauthenticated Bulk Export of Employee, Salary and Bank Data
- **Fix:** Require authenticated, HR-admin-only access for exports; audit and alert on bulk data access.

### Missing Security Headers
- **OWASP:** A05 Security Misconfiguration · **Difficulty:** Beginner · **Severity (in a real client report):** Low
- **What it is:** Security headers are cheap, layered protection: they stop clickjacking, MIME confusion and limit XSS blast radius. Their complete absence signals an unhardened deployment.
- **Business impact:** Without frame protection, the HR portal can be embedded in an attacker's page for clickjacking — tricking an HR admin into clicking hidden admin actions.
- **Report title:** Missing HTTP Security Headers
- **Fix:** Add X-Frame-Options/Content-Security-Policy frame-ancestors, X-Content-Type-Options: nosniff, and Referrer-Policy at the app or proxy layer.


## Files & Documents — 2 test(s)

### Unrestricted File Upload (Stored HTML)
- **OWASP:** A03 Injection · **Difficulty:** Intermediate · **Severity (in a real client report):** High
- **What it is:** Uploads must be allowlisted by type, stored outside the web root or served with a safe content type and Content-Disposition. Serving user HTML from the app origin is stored XSS by another door.
- **Business impact:** An employee uploads a fake "HR login" page hosted on the real HR domain — perfect phishing against colleagues, delivered from a trusted address.
- **Report title:** Unrestricted File Upload Allows Hosting Arbitrary HTML on the Application Origin
- **Fix:** Allowlist file types, verify content, serve uploads with Content-Disposition: attachment or from a separate domain, and never as text/html.

### Path Traversal in Document Download
- **OWASP:** A01 Broken Access Control · **Difficulty:** Intermediate · **Severity (in a real client report):** High
- **What it is:** Never join user input onto filesystem paths without canonicalisation and an allowlist. Traversal turns a document viewer into a full file-read primitive — source, config, secrets.
- **Business impact:** The app's source code — and with it every embedded secret and the full vulnerability map — is readable by any employee, and on a real system config files and credentials follow.
- **Report title:** Path Traversal in Document Download Allows Arbitrary File Read
- **Fix:** Resolve the final path and verify it stays inside the documents directory; serve documents by id from an allowlist, not by filename.
